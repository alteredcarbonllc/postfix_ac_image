# Автоматический деплой почтовой конфигурации

GitHub (`main`, push/manual) → Woodpecker local backend → архив фиксированного
набора конфигурационных файлов → приватный серверный релиз → проверка → применение.
Репозитории: `alteredcarbonllc/dovecot_config` и `alteredcarbonllc/postfix_config`.

Пакет рассчитан на завершённую миграцию почты `switch-y5wjyifr`, установленный
`ac-mailctl` из `ops/mail-switch` и прежние закреплённые образы Dovecot/Postfix.
Он не обновляет образы и не заменяет контейнеры. Штатные письма, очередь, IP,
порты и runit supervisors сохраняются.

## Состав пакета

- `postfix_ac_image/ops/mail-config-ci`: root-инструмент, установщик и tests.
- `dovecot_config/.woodpecker.yaml`, `ops/ci/*`: pipeline и экспортёр Dovecot.
- `postfix_config/.woodpecker.yaml`, `ops/ci/*`: pipeline и экспортёр Postfix.

Существующие настройки в конфигурационных репозиториях пакет не меняет.
`mail_runtime.py` и `mail_release.py` здесь — копии версии для совместимости.
Установщик обновляет только runtime, добавляя блокировку незавершённого
конфигурационного деплоя; установленный release helper сверяется побайтово.
Не запускайте старый `ops/mail-switch/install.py` поверх обновлённого runtime.

## 1. Установка серверной части

Сначала добавить `ops/mail-config-ci` в `postfix_ac_image`, проверить tests,
сделать commit/push и на сервере pull. Из `/root/git/postfix_ac_image`:

```sh
sudo python3 ops/mail-config-ci/install.py
sudo /usr/local/sbin/ac-mail-config status
sudo /usr/local/sbin/ac-mailctl check
```

Установка не перезапускает почту. Она проверяет версии инструментов и текущие
конфигурации, сохраняет их хеши, делает резервную копию runtime, создаёт inbox
и разрешения sudo для `prepare/apply` обоих сервисов. Автоматическое применение
по умолчанию выключено; повторная установка сохраняет текущее состояние флага.
Владельцы новых inbox — `ac-ci-builder` UID 1001, режим 0700, root-owned parent.

Успешный результат: `MAIL_CONFIG_CI_INSTALLED`, затем версии обоих релизов и
`CI_DEPLOY_ENABLED=false`, затем `MAIL_HEALTH_OK`.

## 2. Подключение pipeline

Добавить файлы из соответствующих каталогов пакета в два конфигурационных
репозитория, зафиксировать и отправить на GitHub. Активировать оба репозитория
в Woodpecker с тем же local backend, который уже запускает NGINX pipeline.
Не включать выполнение недоверенных pull requests на этом backend.

Перед первым применением администратор включает автоматический деплой:

```sh
sudo /usr/local/sbin/ac-mail-config enable
```

После этого каждый разрешённый push/manual pipeline автоматически вызывает
`apply SERVICE FULL_SHA`. Файлы вручную в рабочую конфигурацию сервера не копируются,
серверу не нужен `git pull` конфигурационных репозиториев и доступ к их GitHub.
Доступ для clone нужен самому Woodpecker, как и для существующих pipeline.
Если pipeline запускался до установки/включения, перезапустить его в Woodpecker.

Первый commit добавляет только CI-файлы, поэтому при неизменившихся секретах
ожидается `MAIL_CONFIG_NOOP: ...; no restart` для каждого сервиса.
Это проверяет реальную передачу, импорт, подготовку и здоровье почты без
остановки. Для проверки реального применения впоследствии нужен осмысленный
коммит с изменением настроек и проверка почтового клиента после деплоя.

## Как выполняется обновление

Экспортируются только файлы из `git archive FULL_SHA -- SERVICE templates`.
Рабочее дерево должно быть чистым, HEAD совпадать с CI_COMMIT_SHA; имя
репозитория, ветка и событие проверяются pipeline. Pipeline сериализованы
общим `flock` с ожиданием до 600 секунд.

Сервер принимает только известные обычные файлы с ограничением размера;
symlink, hardlink, специальные файлы, дубли и выход за пределы пути запрещены.
Архив копируется через открытый descriptor с проверкой изменения файла и UID.
Файлы и код из `ops/ci` не исполняются серверным root-importer.

SQL credentials читаются из `/etc/ac/secrets/{dovecot,postfix}/sql.json`.
Шаблоны заполняются только в закрытом каталоге сервера. SQL maps не попадают
обратно в inbox или Git. Проверка синтаксиса выполняется в отдельном контейнере
из закреплённого образа, без сети, писем и рабочей очереди.

Новый релиз хранится в `/var/lib/ac-mail/ci-releases/SERVICE/SHA-HASH`.
Повторное предъявление того же SHA с другим исходным содержимым запрещено.
Изменение серверного секрета создаёт другой релиз даже для прежнего commit.
SHA — идентификатор, переданный доверенным CI; этот механизм не является
проверкой подписи GitHub. Доступ к local backend и push в эти репозитории
означает право управлять почтовой конфигурацией, как в существующем NGINX CI.

Если содержимое совпадает с текущим, обновляется запись версии, перезапуска нет.
Если настройки изменились:

1. Проверяются ID/образы/mounts контейнеров, текущее здоровье и отсутствие
   ручных изменений рабочих файлов. Берутся те же блокировки, что у ac-mailctl,
   подготовки релизов и PostgreSQL.
2. Сохраняются содержимое, владелец, группа и режим всех заменяемых файлов.
3. Ставятся down-файлы; останавливаются Postfix, затем Dovecot. Перед первой
   заменой подтверждается остановка обоих контейнеров.
4. Меняются только файлы выбранного сервиса в существующих рабочих bind
   directories. SQL maps получают прежние права и владельцев. Dovecot config
   остаётся read-only внутри контейнера. Postfix сохраняет файлы своего пакета.
5. Запускаются Dovecot, затем Postfix, выполняются проверки `ac-mailctl`:
   userdb, TLS 993/995/587/465, известный получатель, запрет relay и AUTH на 25.
6. Записываются новый релиз и хеши фактических файлов, транзакция завершается.

При изменении одного сервиса кратко останавливается вся пара. Это сознательное
ограничение первой версии: смешанная конфигурация не видна работающим процессам.
Для совместимого изменения обоих сервисов нужны два последовательных деплоя;
пакет не обещает атомарного обновления двух отдельных Git commits одновременно.

## Откат и восстановление

При ошибке применения инструмент останавливает пару, восстанавливает сохранённые
файлы, затем запускает прежнюю конфигурацию и проверяет здоровье. Контейнеры,
письма и очередь остаются прежними; данные не откатываются из tar.

Если остановку подтвердить нельзя, старые файлы не устанавливаются поверх
работающих процессов. Сохраняется `/var/lib/ac-mail/pending-config.json`.
Для восстановления после обрыва процесса или сбоя отката:

```sh
sudo /usr/local/sbin/ac-mail-config recover
```

До завершения recovery команды управления из `ac-mailctl` блокируются.
Служебные команды runit `run/signal-stop` продолжают работать, чтобы транзакция
могла штатно остановить и запустить контейнеры. Вручную обходить down-файлы
или запускать Podman во время recovery не нужно.

`recover` предназначен для незавершённой операции. Откат успешно применённой
версии выполняется новым Git commit (`git revert` нужного изменения) и CI.

## Состояние, рабочие каталоги и отчёты

```sh
sudo ac-mail-config status
sudo ac-mailctl check
sudo ac-mail-config disable   # выключить следующие CI-применения
```

`active-config.json` — актуальные версии настроек и хеши рабочих файлов.
`active.json` от первоначальной миграции продолжает описывать контейнеры и
их mounts; поле `release` в нём остаётся исходным bootstrap-релизом.
Для текущей версии конфигурации использовать `ac-mail-config status`.

Рабочие файлы остаются в `/var/lib/ac-mail/switch-y5wjyifr/...`; эти каталоги
нельзя удалять. Новые неизменяемые релизы, приватные отчёты проверки и snapshots
хранятся отдельно. Ротация этих каталогов не входит в пакет.

Отчёты `ci-releases/.../.prepare-*` и `config-deploy-*` приватные: могут содержать
SQL credentials и конфигурационные ошибки. Не публиковать целиком.

Набор допустимых файлов намеренно фиксирован текущей структурой двух репозиториев.
Добавление нового файла, изменение топологии, образа или mounts требует отдельного
обновления серверного инструмента. Это не деплой произвольных файлов в контейнер.

## Проверки разработки

```sh
python3 -m unittest discover -s ops/mail-config-ci/tests -v
```

Tests покрывают опасные tar entries, повторный импорт, коллизию SHA,
ротацию секрета, drift, no-op, успешное применение, откат после запуска,
отказ остановки, прерванную замену и блокировку обычного runtime.
Podman/systemd/настоящая почта здесь не моделируются полностью: первый серверный
импорт и последующее применение необходимо проверить по выводу pipeline.
